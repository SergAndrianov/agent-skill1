# ПлатиДом — автоплатёж с лимитом суммы

[DSL](workspace.dsl) · [Диаграмма](AutopayLimit.svg) · [Проверка](check.md) · представление `AutopayLimit`.

Клиент настраивает автоплатёж для собственной привязки и видит результат либо причину пропуска в мобильном банке. Управление настройкой описано в SCRUM-2167, исполнение и сверка результата — в SCRUM-2168. Обе истории связаны с фичей SCRUM-2166 отношением `relates to`. [SCRUM-2166](https://javacode.atlassian.net/browse/SCRUM-2166), [SCRUM-2167](https://javacode.atlassian.net/browse/SCRUM-2167), [SCRUM-2168](https://javacode.atlassian.net/browse/SCRUM-2168).

## Исполнение, отключение и восстановление

Следующие переходы детализируют проектное допущение A-17. Один процесс обработчика выполняет и планирование, и обработку заданий. Момент запуска планирования остаётся вопросом Q-01. При срабатывании обработчик читает собственные привязки правил и подходящие начисления, формирует готовую работу в PostgreSQL. PostgreSQL хранит также срок следующей сверки уже созданной попытки. Настройки и история обслуживаются API независимо от выполнения заданий.

1. **Захват работы.** Один экземпляр атомарно переводит готовое задание во владение с уникальным маркером и сроком по часам БД. Конкуренты берут другие строки. Владелец продлевает срок только при действующем маркере. Все переходы проверяют маркер и статус записи. После истечения срока до выдачи допуска к отправке другой экземпляр может заново провести проверки. Запоздавший владелец теряет право менять запись. Уникальность задания и платежа защищена ограничением БД по стабильному ключу начисления из источника и его подтверждённой области уникальности. Идентификатор доставки события, версия правила и источник оплаты в ключ начисления не входят. До подтверждения области уникальности, срока защиты и сопоставления повторов действует ограничение допуска по Q-05.
2. **Проверки и допуск.** Владелец получает начисление по сохранённой привязке. Проверяет владельца, актуальность, неоплаченность, валюту, положительную сумму и сравнение с лимитом `0 < сумма ≤ лимит`. Обработчик передаёт внешнему владельцу проверок ссылку на инструмент и сумму для совмещённой проверки доступности и средств. При отрицательном результате фиксирует причину пропуска. При недоступных или устаревших данных допуск закрыт до получения достоверных сведений. Q-02 определяет допустимый возраст данных и реакцию на изменение суммы. Q-06 определяет доступные инструменты, учёт комиссии и способ подтвердить достаточность при конкурирующих расходах. Для выпуска одной предварительной оценки средств недостаточно, если она может устареть к отправке. Нужна подтверждённая гарантия на момент допуска, например действующий резерв, и атомарная проверка средств владельцем списания. Дополнительный вызов за резервом потребует пересчёта нагрузки.
3. **Одна команда на попытку.** В транзакции по правилу и заданию обработчик перечитывает владельца, активность и версию правила, проверяет владение, допустимость результатов проверок и отсутствие запроса на отключение. Устаревшая версия требует заново проверить условия. Уникальный переход открывает однократный допуск текущему владельцу. До отправки PostgreSQL сохраняет неизменяемые идентификатор начисления, полную сумму и валюту, ссылку на инструмент и ключ операции ПлатиДома. Обработчик передаёт их процессингу. Ключ операции предназначен для сверки и распознавания повторов по A-09. Идентификатор процессинга появляется из ответа или последующей сверки. Маркер владения обслуживает захват в БД. Повтор события, перезапуск или новый владелец записи не открывают второй допуск после перехода к отправке. Автоматические повторы команды на транспортном уровне выключены.
4. **Гонка с отключением и изменением.** Операции API и выдача допуска используют общую запись правила и сериализуются по ней. Запрос на отключение сразу закрывает выдачу новых допусков. Если открытого допуска нет, API сохраняет «отключено» в той же транзакции. При открытом допуске перед выходом в транспорт обработчик проверяет, что он действителен и запрос на отключение отсутствует. Если запрос уже записан и передача ещё не началась, обработчик закрывает допуск и фиксирует пропуск. Если запрос пришёл после последней проверки, API ждёт подтверждённой границы. Это либо необратимая передача команды транспорту, либо доказанное закрытие допуска без возможности последующей передачи. Лишь затем API сохраняет «отключено» и подтверждает его клиенту. Изменение использует ту же границу, подтверждённая новая конфигурация применяется к ещё не переданным попыткам (A-11). Переданную операцию продолжают сверять.
5. **Сбой в окне отправки.** Истечение срока в PostgreSQL после выдачи допуска само по себе не доказывает, что прежний исполнитель перестал иметь возможность отправить команду. Открытый допуск переживает сбой. Новый владелец получает только сверку, а API продолжает блокировать новые допуски и ждёт безопасной границы перед подтверждением отключения. Если запись о передаче потеряна, границу можно подтвердить квитанцией о необратимой передаче, доказанной остановкой прежнего исполнителя вместе с его транспортом или согласованным отзывом допуска, который принимающая сторона проверяет атомарно при создании операции. Поддержка отзыва не подтверждена. Точное поведение интерфейса при длительном ожидании и технический способ доказать эту границу предстоит согласовать. Если передачу и закрытие допуска нельзя надёжно упорядочить, отправку по модели не разрешают (A-17).
6. **Уточнение результата.** При тайм-ауте, потере ответа или обнаружении незавершённой попытки после сбоя обработчик сохраняет «результат уточняется». Владелец задания сверки читает состояние первоначальной операции по ID процессинга, когда он известен. Иначе используется сохранённый ключ ПлатиДома, если процессинг гарантирует по нему поиск исходной операции. Если такой поиск недоступен, операция остаётся на уточнении, наступает согласованная эскалация по Q-03. Ответ «не найдено» сам по себе не даёт права повторить отправку. Лишь подтверждённый успех даёт статус «успешно» с суммой и идентификатором, явный отказ — статус «отклонено» с причиной. Повторные чтения состояния допустимы. Правила тайм-аутов, интервалов и эскалации открыты (Q-03), повтор после окончательного отказа выключен до решения Q-04, запоздалые и противоречивые результаты требуют контракта Q-09. Пока гарантии распознавания и сверки операции по A-09 не подтверждены, допуск к отправке закрыт.

## Расчёт нагрузки и ёмкость

A-16 задаёт 25 000 начислений-кандидатов в сутки, 40% в наиболее загруженный час и кратковременный всплеск ×3. Это учебные вводные. На пик приходится `25 000 × 0,40 = 10 000` кандидатов за час. При всплеске интенсивность `λ = 10 000 ÷ 3 600 × 3 ≈ 8,33` кандидата в секунду. Для совместного пика поиск и обновление из соседней фичи добавляют `20 000 × 0,30 ÷ 3 600 × 5 ≈ 8,33` вызова ГИС ЖКХ и до `8,33 × (1 + 0,35) ≈ 11,25` транзакции записи в секунду по A-15.

| Поток | На кандидата | Пик автоплатежа | Совпадение пиков с поиском | Совпадение пиков при удвоении объёмов |
|---|---:|---:|---:|---:|
| ГИС ЖКХ, чтение начисления | 1 | 8,33/с | 16,67/с | 33,33/с |
| Владелец проверки инструмента и средств | 1 | 8,33/с | 8,33/с | 16,67/с |
| Процессинг, команды оплаты | до 1 | 8,33/с | 8,33/с | 16,67/с |
| Процессинг, чтения статуса | 2 в расчётном окне | 16,67/с | 16,67/с | 33,33/с |
| Все внешние вызовы фонового потока и поиска из строк выше | до 5 для автоплатежа | 41,67/с | 50,00/с | 100,00/с |
| Транзакции записи в PostgreSQL по этим потокам | до 9 для автоплатежа | 75,00/с | 86,25/с | 172,50/с |

Если совмещённую проверку выполняет процессинг, четыре внешних вызова на кандидата приходятся на одного адресата. Это до `4 × λ ≈ 33,33/с`, при удвоении — около `66,67/с`. Две сверки — вводная A-16. Пик накопленных сверок после сбоя моделируется дополнительно. В оценку записи взяты отдельные транзакции на постановку задания, захват, решение о допуске или пропуске, запись передачи или закрытия допуска и запись первого исхода. Две сверки добавляют до двух транзакций на каждую, захват и сохранение результата. Итого `5 + 2 × 2 = 9`. Чтения, продления владения, повторы условных записей, команды управления правилом, проверки источников на активации и чтения истории учитываются отдельно после замера профиля. Число SQL-операторов внутри транзакции может быть больше одного.

Мобильное приложение и API обслуживают действия клиента. Третье приложение выполняет фоновый поток с собственным запуском, обратным давлением и независимым числом исполнителей по A-17. Его задержки определяют длину очереди и не занимают обработчики запросов API. Один логический экземпляр PostgreSQL нужен для общих транзакций по уникальности начисления, праву на отправку и изменениям правила. Таблицы готовой работы и сверки позволяют делить работу между экземплярами без отдельного брокера на учебном объёме. Параллелизм увеличивает скорость по разным правилам и начислениям. Одно правило кратко сериализует операции допуска, изменения и отключения, одно начисление — создание платежа. Ожидание ответа от внешней системы идёт вне транзакции БД. Требуемое число одновременных вызовов зависимости с длительностью `T` секунд оценивается по формуле `интенсивность × T`, затем ограничивается её квотой и размером пула. Число экземпляров и запас ёмкости предстоит определить измерениями.

## Проверки реализации перед допуском

- Воспроизвести захват двумя экземплярами, продление владения, истечение срока и возобновление прежнего процесса. Повторить со сбоем до допуска, после допуска до передачи, после передачи до записи подтверждения, при ответе, потерянном до получения внешнего ID. Проверить число команд, неизменность ключа операции и переход к сверке.
- Синхронизировать отключение с последней проверкой и началом передачи. Проверить случаи отключения до захвата, после захвата и до допуска, при открытом допуске до передачи, между последней проверкой и передачей, после передачи. Отдельно потерять связь прежнего обработчика с БД и возобновить его после замены. Проверить, что подтверждённое отключение следует за безопасной границей и после него команда по правилу не уходит. Аналогично проверить смену лимита при той же гонке.
- Контрактными тестами подтвердить идентичность начисления, актуальность данных, проверку средств при нескольких конкурирующих платежах с одного инструмента, состав суммы, распознавание ключа и получение статуса до появления внешнего ID. Проверить неизвестный исход, «не найдено», окончательный отказ, запоздалые и противоречивые ответы.
- При одиночном пике, совпадении пиков и удвоении объёмов измерить p95/p99 API и обработки задания, длину и возраст очереди, просроченные сверки, время отключения, ожидание блокировок и загрузку PostgreSQL, пула соединений и внешних квот. Добавить медленные ответы, тайм-ауты и восстановление внешних систем при накопившейся очереди. Целевые задержки и предел сверки согласуются с контрактами.
