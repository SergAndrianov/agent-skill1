# ПлатиДом — автоплатёж с лимитом суммы

[DSL](workspace.dsl) · [Диаграмма](AutopayLimit.svg) · [Проверка](../../scrum-2166-rerun-check.md) · представление `AutopayLimit`.

Клиент настраивает автоплатёж для собственной привязки и видит результат либо причину пропуска в мобильном банке. Управление настройкой описано в SCRUM-2167, исполнение и сверка результата — в SCRUM-2168. Обе истории связаны с фичей SCRUM-2166 отношением `relates to`. [SCRUM-2166](https://javacode.atlassian.net/browse/SCRUM-2166), [SCRUM-2167](https://javacode.atlassian.net/browse/SCRUM-2167), [SCRUM-2168](https://javacode.atlassian.net/browse/SCRUM-2168).

## Исполнение, отключение и восстановление

Следующие переходы детализируют проектные допущения A-17 и A-18. Один процесс обработчика выполняет и планирование, и обработку заданий. Момент запуска планирования остаётся вопросом Q-01. При срабатывании обработчик читает собственные привязки правил и подходящие начисления, формирует готовую работу в PostgreSQL. PostgreSQL хранит также срок следующей сверки уже созданной попытки. Настройки и история обслуживаются API независимо от выполнения заданий.

1. **Захват работы.** Один экземпляр атомарно переводит готовое задание во владение с уникальным маркером и сроком по часам БД. Конкуренты берут другие строки. Владелец продлевает срок только при действующем маркере. Все переходы проверяют маркер и статус записи. После истечения срока до выдачи допуска к отправке другой экземпляр может заново провести проверки. Запоздавший владелец теряет право менять запись. Уникальность задания и платежа защищена ограничением БД по стабильному ключу начисления из источника и его подтверждённой области уникальности. Идентификатор доставки события, версия правила и источник оплаты в ключ начисления не входят. До подтверждения области уникальности, срока защиты и сопоставления повторов действует ограничение допуска по Q-05.
2. **Проверки и допуск.** Владелец получает начисление по сохранённой привязке. Проверяет владельца, актуальность, неоплаченность, валюту, положительную сумму и сравнение с лимитом `0 < сумма ≤ лимит`. Обработчик передаёт внешнему владельцу проверок ссылку на инструмент и сумму для совмещённой проверки доступности и средств. При отрицательном результате фиксирует причину пропуска. При недоступных или устаревших данных допуск закрыт до получения достоверных сведений. Q-02 определяет допустимый возраст данных и реакцию на изменение суммы. Q-06 определяет доступные инструменты, учёт комиссии и способ подтвердить достаточность при конкурирующих расходах. Для выпуска одной предварительной оценки средств недостаточно, если она может устареть к отправке. Нужна подтверждённая гарантия на момент допуска, например действующий резерв, и атомарная проверка средств владельцем списания. Дополнительный вызов за резервом потребует пересчёта нагрузки.
3. **Одна команда на попытку.** Обработчик в транзакции под блокировкой правила и задания проверяет владельца, состояние и версию правила, действующее владение и результаты проверок. Смена версии до допуска требует повторной проверки. Уникальный переход фиксирует однократный допуск, ID начисления, полную сумму, валюту, ссылку на инструмент, ключ операции и неизменяемый срок приёма. Срок равен времени выдачи по часам БД плюс согласованное максимальное окно. Срок владения заданием и срок приёма команды независимы. Перед отправкой обработчик проверяет, что окно открыто и запрос на отключение ещё не записан. Команда отправляется однократно, автоматические транспортные повторы выключены. По A-18 процессинг проверяет срок и ключ атомарно с первым устойчивым принятием операции. При истечении срока или невозможности гарантировать согласованный предел расхождения часов процессинг не принимает новую операцию.
4. **Гонка с отключением и изменением.** API и выдача допуска сериализуются по записи правила в PostgreSQL. Отключение сразу блокирует новые допуски и сохраняет момент вступления в силу. Для каждого выданного допуска безопасная граница равна сроку приёма плюс согласованное предельное расхождение часов БД и процессинга. Правило отключено сразу, если по часам БД все такие границы уже достигнуты либо допуски ещё не выдавались. Иначе момент равен самой поздней из этих границ. До него API возвращает переходное состояние «отключается», после него — «отключено». Состояние вычисляется при чтении правила по часам БД и сохранённому моменту. Оно не ждёт ответа процессинга, восстановления обработчика или отдельного задания. Повтор отключения сохраняет прежний момент. При гонке изменения тот же порядок закрывает выдачу старых допусков. Новая конфигурация вступает в силу после закрытия их окон и проверяется заново для ещё не отправленных попыток (A-11).
5. **Сбой в окне отправки.** Если обработчик упал до допуска, работу можно забрать заново только при действующем правиле. Если сбой случился после допуска, новый владелец сверяет исход по сохранённому ключу и не отправляет повтор. Даже при потере ответа и возобновлении старого процесса просроченная команда не создаст операцию в процессинге благодаря A-18. После сохранённого момента отключения новые попытки не запускаются и поздняя доставка не создаёт новый платёж. Операция, принятая раньше, продолжает отслеживаться. Пропуск фиксируется, когда отправки точно не было или процессинг подтвердил, что операция по ключу не была принята и окно закрыто. При неопределённости остаётся сверка. Без подтверждения A-18 обработчик не получает допуск к отправке, поэтому отключение такого правила не ждёт внешнего ответа.
6. **Уточнение результата.** При тайм-ауте, потере ответа или обнаружении незавершённой попытки после сбоя обработчик сохраняет «результат уточняется». Владелец задания сверки читает состояние первоначальной операции по ID процессинга, когда он известен. Иначе используется сохранённый ключ ПлатиДома, если процессинг гарантирует по нему поиск исходной операции. Если такой поиск недоступен, операция остаётся на уточнении, наступает согласованная эскалация по Q-03. Ответ «не найдено» сам по себе не даёт права повторить отправку. Лишь подтверждённый успех даёт статус «успешно» с суммой и идентификатором, явный отказ — статус «отклонено» с причиной. Повторные чтения состояния допустимы. Правила тайм-аутов, интервалов и эскалации открыты (Q-03), повтор после окончательного отказа выключен до решения Q-04, запоздалые и противоречивые результаты требуют контракта Q-09. Пока не подтверждены гарантии A-09 и A-18, допуск к отправке закрыт.

## Расчёт нагрузки и ёмкость

A-16 задаёт 25 000 начислений-кандидатов в сутки, 40% в наиболее загруженный час и кратковременный всплеск ×3. Это учебные вводные. На пик приходится `25 000 × 0,40 = 10 000` кандидатов за час. При всплеске интенсивность `λ = 10 000 ÷ 3 600 × 3 ≈ 8,33` кандидата в секунду. Для совместного пика поиск и обновление из соседней фичи добавляют `20 000 × 0,30 ÷ 3 600 × 5 ≈ 8,33` вызова ГИС ЖКХ и до `8,33 × (1 + 0,35) ≈ 11,25` транзакции записи в секунду по A-15.

| Поток | На кандидата | Пик автоплатежа | Совпадение пиков с поиском | Совпадение пиков при удвоении объёмов |
|---|---:|---:|---:|---:|
| ГИС ЖКХ, чтение начисления | 1 | 8,33/с | 16,67/с | 33,33/с |
| Владелец проверки инструмента и средств | 1 | 8,33/с | 8,33/с | 16,67/с |
| Процессинг, команды оплаты | до 1 | 8,33/с | 8,33/с | 16,67/с |
| Процессинг, чтения статуса | 2 в расчётном окне | 16,67/с | 16,67/с | 33,33/с |
| Все внешние вызовы фонового потока и поиска из строк выше | до 5 для автоплатежа | 41,67/с | 50,00/с | 100,00/с |
| Транзакции записи в PostgreSQL по этим потокам | до 9 для автоплатежа | 75,00/с | 86,25/с | 172,50/с |

Если совмещённую проверку выполняет процессинг, четыре внешних вызова на кандидата приходятся на одного адресата. Это до `4 × λ ≈ 33,33/с`, при удвоении — около `66,67/с`. Две сверки — вводная A-16. Пик накопленных сверок после сбоя моделируется дополнительно. В оценку записи взяты отдельные транзакции на постановку задания, захват, решение о допуске или пропуске, запись передачи или закрытия допуска и запись первого исхода. Две сверки добавляют до двух транзакций на каждую, захват и сохранение результата. Итого `5 + 2 × 2 = 9`. Чтения, продления владения, повторы условных записей, команды управления правилом, проверки источников на активации и чтения истории учитываются отдельно после замера профиля. Число SQL-операторов внутри транзакции может быть больше одного.

Мобильное приложение и API обслуживают действия клиента. Третье приложение выполняет фоновый поток с собственным запуском, обратным давлением и независимым числом исполнителей по A-17. Его задержки определяют длину очереди и не занимают обработчики запросов API. Один логический экземпляр PostgreSQL нужен для общих транзакций по уникальности начисления, праву на отправку и изменениям правила. Таблицы готовой работы и сверки позволяют делить работу между экземплярами без отдельного брокера на учебном объёме. Параллелизм увеличивает скорость по разным правилам и начислениям. Одно правило кратко сериализует операции допуска, изменения и отключения, одно начисление — создание платежа. Ожидание ответа от внешней системы идёт вне транзакции БД. Требуемое число одновременных вызовов зависимости с длительностью `T` секунд оценивается по формуле `интенсивность × T`, затем ограничивается её квотой и размером пула. Число экземпляров и запас ёмкости предстоит определить измерениями.

- Воспроизвести захват двумя экземплярами, продление владения, истечение срока и возобновление прежнего процесса. Повторить со сбоем до допуска, после допуска до передачи, после передачи до записи подтверждения, при ответе, потерянном до получения внешнего ID. Проверить число команд, неизменность ключа операции и переход к сверке.
- Синхронизировать отключение с последней проверкой и началом передачи. Проверить случаи отключения до захвата, после захвата и до допуска, при открытом допуске до передачи, между последней проверкой и передачей, после передачи.
