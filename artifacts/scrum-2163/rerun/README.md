# ПлатиДом — поиск и привязка начислений по лицевому счету

[DSL](workspace.dsl) · [Диаграмма](SearchAndBind.svg) · [Проверка](../../scrum-2163-rerun-check.md) · представление `SearchAndBind`.

Авторизованный клиент может узнать начисления по введённому лицевому счёту, явно сохранить привязку и при следующем входе запросить начисления без повторного ввода реквизитов. Поиск описан в SCRUM-2164, сохранение и повторный просмотр — в SCRUM-2165. [SCRUM-2163](https://javacode.atlassian.net/browse/SCRUM-2163), [SCRUM-2164](https://javacode.atlassian.net/browse/SCRUM-2164), [SCRUM-2165](https://javacode.atlassian.net/browse/SCRUM-2165).

## Контейнеры и границы

| Элемент | Ответственность | Технология и основание |
|---|---|---|
| Мобильное приложение банка (`mobile`) | Принимает поставщика и лицевой счёт, показывает результат, предлагает явное подтверждение, выводит список своих привязок и сообщения об ошибках. | iOS / Android и HTTPS/JSON к API по A-14. |
| API ПлатиДома (`api`) | Проверяет сессию и доступ, валидирует реквизиты, запрашивает источник, сохраняет успешный результат и исполняет команду привязки. | Java / Spring Boot, SQL/JDBC к БД по A-14. |
| База данных ПлатиДома (`db`) | Хранит привязки, успешные результаты поиска или обновления и время их получения. Обеспечивает уникальность привязки. | PostgreSQL по A-14. |

Снаружи границы ПлатиДома (`platidom`) находятся клиент (`client`) и источник начислений (`accrualSource`). Источник в учебной модели — ГИС ЖКХ по A-01. API передаёт идентификатор выбранного поставщика и лицевой счёт. Для этой связи предстоит уточнить протокол и признаки, по которым API различает найденные начисления, успешный пустой результат и сбой (A-01, A-12, A-14). Контракт банковской сессии открыт по A-14. Правила формата зависят от поставщика по A-02. Способы подтверждения валидности и принадлежности счёта остаются открытым вопросом Q-08. A-03 допускает привязку после успешного пустого поиска по валидному счёту. Юридическая принадлежность счёта лежит вне сценария привязки.

На диаграмме фигура человека обозначает клиента, синяя рамка устройства — мобильное приложение, синий прямоугольник — API, цилиндр — хранилище, серый блок — внешнюю систему. Стрелка направлена от инициатора к получателю. Синие стрелки выделяют подтверждение и запись данных. [Контейнерная диаграмма C4](https://c4model.com/diagrams/container), [Рекомендации Дмитрия Фролова и Владимира Мясникова](https://habr.com/ru/companies/nspk/articles/679426/).

|---|---|---|---|---|
| 1. Корректные реквизиты (BR-02, BR-03) | Клиент авторизован, выбирает поставщика, вводит корректный лицевой счёт и запускает поиск. | Мобильный банк передаёт реквизиты API. API проверяет ввод и запрашивает источник по поставщику и счёту. | API сохраняет результат поиска, связанный с текущим клиентом, и время его получения. ### SCRUM-2165 — привязать лицевой счёт и просматривать начисления

| Критерий | Исходное состояние и действие | Ответственность и вызов | Изменение данных | Результат для клиента |
|---|---|---|---|---|
| 1. Явное подтверждение (BR-05, A-03) | Клиент успешно завершил поиск, в том числе с пустым результатом, и подтверждает сохранение. | Мобильный банк отправляет отдельную команду с ID поиска. API в транзакции проверяет принадлежность успешного поиска и берёт из него поставщика и лицевой счёт. | В профиле сохраняется привязка с результатом и временем его получения. | После фиксации транзакции мобильный банк показывает подтверждение и сохранённую привязку. |
| 2. Повторное сохранение (BR-06) | Привязка уже существует, клиент повторно подтверждает тот же счёт у того же поставщика. | API использует уникальный ключ `клиент + поставщик + лицевой счёт`. При конфликте записи PostgreSQL API возвращает существующую привязку. | Одна привязка на комбинацию, в том числе при одновременных подтверждениях. | Возвращён ID существующей привязки, включая повтор после потери ответа. |
| 3. Следующий вход (BR-07) | Клиент повторно входит и выбирает сохранённую привязку. | API читает список привязок клиента, затем по ID выбранной привязки и владельцу извлекает поставщика и счёт. С ними запрашивает источник. | При успехе сохраняется новый результат и время обновления. | Клиент видит свою привязку и полученные от источника начисления без повторного ввода счёта. |
| 4. Ошибка обновления (BR-08) | Клиент обновляет свою привязку, источник не отвечает успешно. | API возвращает ошибку и последний успешный результат из PostgreSQL при его наличии. | — | Ранее полученные данные помечены как неактуальные с временем последнего успеха. При отсутствии сохранённых сведений показана ошибка обновления. |
| 5. Чужая привязка (BR-01) | Клиент подставляет чужой ID в запросе чтения или изменения привязки. | API ограничивает выборку по ID текущим клиентом. Чужой или неизвестный ID приводят к одинаковому отказу до выдачи данных или изменения привязки. Вызовов источника — 0. | — | Запрос отклонён, ответ содержит только ошибку. |

## Расчёт нагрузки и выбор архитектуры

Все объёмы — учебные вводные A-15. Нагрузка поиска включает обращения по введённым реквизитам и по сохранённой привязке. Чтение списка привязок учитывается дополнительно, его интенсивность требуется измерить.

| Величина | Расчёт | Оценка |
|---|---|---|
| Поиск, самый загруженный час | 20 000 запросов/сутки × 30% | 6 000 запросов/час |
| Поиск при кратковременном всплеске | 6 000 ÷ 3 600 × 5 | ≈ 8,33 запроса/с |
| Подтверждение привязки | 8,33 × 35% | ≈ 2,92 запроса/с |
| Мобильный банк → API | Поиск + подтверждение | ≈ 11,25 запроса/с плюс чтение списка привязок |
| API → ГИС ЖКХ | До одного вызова на каждый поиск | До ≈ 8,33 вызова/с |
| Записи в PostgreSQL | До одной транзакции на поиск + одна на подтверждение | До ≈ 11,25 транзакции записи/с плюс отдельные чтения привязок и сохранённых результатов |

Два приложения соответствуют двум средам исполнения. Мобильное приложение ведёт диалог с клиентом, API выполняет запрос целиком в пределах пользовательского обращения. При расчётных 8,33 вызова источника в секунду достаточно начать с одного серверного приложения с ограничением числа одновременных вызовов. Задержки источника определяют количество одновременно занятых запросов API: при длительности вызова `T` секунд это около `8,33 × T` запросов на расчётном пике. Одна PostgreSQL позволяет при подтверждении одной транзакцией проверить результат поиска, создать привязку и применить ограничение уникальности. Число экземпляров API определяется нагрузочным тестом.

Нагрузочному тесту нужно воспроизвести расчётный пик с поиском по обоим входам, чтением списков и долей подтверждений 35%, добавить замедление, тайм-ауты и восстановление источника. Измерить p95/p99 для поиска и подтверждения, число одновременных запросов к источнику, долю ошибок, задержки БД, занятость пулов и ожидание на уникальном ключе. Проверить возврат последнего успешного результата при сбое и один ID привязки при одновременных подтверждениях. Целевые задержки и пропускную способность интеграции предстоит сверить с её контрактом.
